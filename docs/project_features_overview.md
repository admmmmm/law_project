# 检察侦查画像系统：项目特点与技术功能设计

本文用于说明当前项目的技术特点、功能边界和核心设计。它不是使用手册，而是给开发者、项目成员和答辩展示时使用的“系统现状说明”。

## 1. 项目定位

本项目面向检察侦查、职务犯罪审查和复杂证据材料梳理场景。系统目标不是替代办案人员作出法律结论，而是把散乱证据组织成可检索、可视化、可溯源的分析工作台。

当前重点能力包括：

- 案件管理与证据导入
- 非结构化证据与结构化流水的统一入库
- HippoRAG / OpenIE 图谱构建与 PPR 检索
- DeepSeek 辅助事实画像、智能分析和问答
- 案件证据地图：文件层、片段层、原始图谱层
- 画像报告的句级溯源
- 检察分析技能包与规则 finding
- 法律知识库和罪名模板接入
- 图谱人工增删改查与核验

项目的基本思路是：

```text
证据材料
  -> 结构化/非结构化抽取
  -> passage 与原始图谱
  -> HippoRAG 关联检索
  -> 文件级证据组织
  -> 规则包发现缺口
  -> DeepSeek 生成可溯源分析
```

## 2. 总体架构

当前系统采用前后端分离结构。

前端：

- Vue 3 + Vite
- `relation-graph/vue3` 作为当前图谱可视化基础
- 页面集中在 `frontend/src/views`
- API 封装在 `frontend/src/api/backend.ts`

后端：

- FastAPI
- Pydantic schema
- SQLite / 本地运行机器持久化
- `MemoryStore` 作为当前统一存储抽象
- HippoRAG 代码内置在 `backend/app/hipporag`
- DeepSeek 通过兼容 OpenAI API 的方式调用

主要后端模块：

```text
backend/app/services/
  ingestion_service.py              证据导入
  information_extraction.py         结构化/非结构化抽取
  graph_service.py                  图谱读写与人工干预
  evidence_map_service.py           案件证据地图
  document_mother_service.py        文件级证据节点
  analysis_skill_service.py         检察分析技能包
  retrieval_planner_service.py      Agentic RAG 检索计划器
  analysis_service.py               智能分析与会话
  report_service.py                 画像报告
  legal_knowledge_service.py        法律知识库
```

## 3. 数据导入与证据处理

系统支持将案件证据作为文件夹或压缩包导入。当前支持类型包括：

- `txt`
- `md`
- `csv`
- `xlsx`
- `json`
- `pdf`
- `docx`
- `zip`

导入后的证据会成为 `EvidenceRecord`，并保留：

- 证据 ID
- 案件 ID
- 标题
- 来源类型
- 原始内容预览
- 原文内容
- 创建时间

### 3.1 非结构化证据

非结构化证据包括笔录、报告、决定书、通知书、短信打印件等。

处理流程：

```text
原始文档
  -> 切分 passage
  -> OpenIE 抽取实体和关系
  -> 生成图谱节点/边
  -> 保留 evidence_id 与 passage 关联
```

非结构化材料的核心问题是“事实不能脱离原文”。因此系统尽量保留 passage，后续点击分析结论时可以回到证据原文。

### 3.2 结构化证据

结构化证据主要包括：

- 银行流水
- 通话记录
- 短信记录
- 案情梳理表
- 人名映射表

结构化数据不应像普通文本一样完全交给 OpenIE 猜测。系统当前设计是优先使用结构化解析，保留：

- 交易时间
- 交易主体
- 对手方
- 金额
- 通话/短信时间
- 主叫/被叫
- 映射后的真实姓名
- 原始别名或账户名

这类数据进入图谱时，应当尽量保持精确字段，而不是让模型二次抽取导致膨胀或幻觉。

## 4. 图谱构建设计

系统中目前存在几类图谱或图谱视图。

### 4.1 原始图谱

原始图谱是系统最细粒度的实体关系图，来自：

- OpenIE 三元组
- 结构化流水解析
- 通话记录解析
- 手工添加节点/关系
- 算法节点

节点包含：

- `node_id`
- `label`
- `type`
- `tags`
- `properties`
- `evidence_ids`
- `timestamp`
- `time_range`
- `manually_verified`

关系包含：

- `edge_id`
- `source_id`
- `target_id`
- `relation`
- `tags`
- `confidence`
- `properties`
- `evidence_ids`
- `timestamp`
- `time_range`
- `manually_verified`

原始图谱适合：

- 查看实体关系
- 查找资金路径
- 查看人物、机构、账户、证据文档节点
- 人工增删改查
- 标记节点或关系已核验

### 4.2 案件证据地图

案件证据地图是图谱页新增的分辨率视图，不是替代原始图谱，而是帮助用户先理解证据结构。

它分三层：

```text
文件层
片段层
原始图谱层
```

三层不是混在一张图里逐级展开，而是不同层级显示不同类型的图。

文件层：

- 节点是证据文件
- 边是文件之间的聚合关系
- 适合看案件证据版图

片段层：

- 节点是 HippoRAG passage / 文本片段
- 边是 passage 之间的关联
- 适合看局部证据链

原始图谱层：

- 保留原来的原始图谱界面
- 节点与边是最细事实图
- 适合做实体级探索和人工维护

### 4.3 文件级证据节点

系统还引入了 `DocumentMotherNode`，用于把每份证据文件组织成一个稳定的文件级节点。

它保存：

- 文书类型
- 流程阶段
- 形成时间
- 事件时间
- 来源质量
- 中性摘要
- 证明事项
- 关键 claim
- 关键实体
- 风险标签
- 生成元数据
- 质量状态

注意：文件级节点本身不负责定罪，也不应该写“构成犯罪”等结论。它的作用是保留证据边界，方便 GraphRAG 式聚合和溯源。

## 5. HippoRAG 与检索设计

项目接入 HippoRAG 的目标是提供多跳关联检索，而不是单纯向量搜索。

HippoRAG 在系统中承担：

- passage indexing
- OpenIE 抽取
- 字符串节点图构建
- Personalized PageRank 检索
- 多跳关联召回
- RAG 问答上下文来源

当前使用方式包括：

- 证据图谱构建时调用 HippoRAG / OpenIE
- `/analysis/trace` 返回 PPR passage 和路径
- 画像报告和智能分析调用检索结果
- 句级溯源时重新检索或绑定已有 passage

### 5.1 Passage 的重要性

系统将 passage 视为证据与模型回答之间的中间层：

```text
模型结论
  -> 支撑 passage
  -> 所属证据文件
  -> 原文内容
```

这比直接把三元组展示给用户更适合办案，因为法律证据最终需要回到原文、来源和形成过程。

### 5.2 多轮检索计划器

项目已经开始引入 Agentic RAG 检索计划器，目标是从“后端固定 query”走向“模型参与规划检索”。

第一版工具包括：

- `search_documents`
- `search_graph`
- `expand_node`
- `search_time_range`
- `search_legal`
- `list_rule_packs`
- `run_rule_pack`
- `get_document_mother_graph`

计划器记录：

- 检索轮次
- 工具调用
- passage
- graph facts
- legal passages
- rule findings
- 缺口评估

前端不展示模型内部推理链，只展示可解释的工具调用摘要和检索记录。

## 6. DeepSeek 使用边界

DeepSeek 在项目中主要用于：

- OpenIE / NER
- RAG 问答
- 画像报告生成
- 智能分析对话
- 假设验证
- 可疑资金流分析
- 文件摘要类字段生成

当前设计强调：

1. DeepSeek 可以写分析，但不能凭空决定规则命中。
2. DeepSeek 输出的结论需要尽量绑定 passage。
3. 对于文件级摘要和 key claims，后端需要 schema 校验。
4. 无 passage 支撑的 claim 应标记为 `unverified_claim`。
5. 规则 findings 不应依赖 DeepSeek 自由文本。

也就是说，系统正在从“模型直接写答案”转向：

```text
结构化证据 + 图谱 + 规则包 + 检索结果
  -> DeepSeek 解释和组织语言
```

## 7. 智能分析页

智能分析页用于处理事实画像之外的探索性问题，当前主要支持：

- 假设验证
- 可疑资金流分析
- 多轮对话
- 会话卡片保存
- 会话删除
- 继续追问
- @证据 指定材料
- 回答句级溯源

用户可以提出：

- “杨周武是否可能对某些文件做了篡改？”
- “资金流是否存在过桥账户？”
- “通话、短信和处置文书之间有没有时间对应？”

系统会通过 RAG 检索、图谱上下文和法律知识库组织答案。

设计原则：

- 分析结果是“疑点画像”或“核查方向”，不是事实结论。
- 检察官可以采纳疑点，后续进入画像页或报告页。
- 多轮会话应保存在后端，切页后不丢失。

## 8. 画像页与画像报告

画像页当前分为两个方向：

### 8.1 事实画像

事实画像重点是：

- 还原人物关系
- 还原行为链条
- 围绕嫌疑人向外扩展
- 尽量基于证据事实，不混入复杂推断

它适合回答：

```text
谁和谁发生了什么关系？
嫌疑人做了哪些关键行为？
时间顺序是什么？
哪些证据支撑这些事实？
```

### 8.2 详细画像报告

详细画像报告更接近正式分析输出，目标包括：

- 基础信息聚合
- 行为事实还原
- 行为方式分析
- 要件核查
- 证据归类
- 缺口标红
- 抗辩预判
- 参考建议

报告中的句子应当能够点击查看：

- 证据原文
- HippoRAG PPR passage
- 图谱路径

当前仍在持续改进的关键点是：每一句结论在生成时就绑定支撑 passage，而不是事后再用相似度检索。

## 9. 检察分析技能包

项目引入了类似 Claude Skills 的“检察分析技能包”机制。

技能包目录：

```text
backend/app/analysis_skills/packs/
  authority_control/
  document_completeness/
  process_turning_point/
```

每个技能包包含：

- `manifest.json`
- `SKILL.md`
- `checks.json`
- `finding_templates.json`
- 示例与测试数据

当前内置技能包：

1. 材料完整性分析
2. 程序转向分析
3. 权限控制分析

技能包的作用不是直接定罪，而是生成 finding：

- 支撑文件
- 支撑 claim
- 缺失材料
- 数据缺口
- 下一步核查建议
- 规则未命中原因

这让系统从“模型自由分析”转向“规则定骨架、模型写解释”。

## 10. 法律知识库与罪名模板

系统中有独立的法律知识库目录：

```text
data/legal_knowledge/
```

当前设计包括：

- 十四种罪名模板
- 法律条文
- 司法解释
- 证据标准材料
- 办案流程知识
- 用户上传的规则/流程材料

案件管理页支持选择罪名。第一版只允许单选，也允许留空。

如果选择罪名：

- 分析 prompt 会更聚焦该罪名
- 法律知识 RAG 会优先召回相关构成要件
- 规则包可以根据案由选择适用范围

如果留空：

- 系统就事论事，不强行套罪名框架。

## 11. 办案流程先验

项目正在补入“正常办案流程图”作为系统先验。

典型流程：

```text
接警
  -> 受案登记
  -> 伤情鉴定/送检
  -> 是否达到刑事立案标准
  -> 立案
  -> 侦查措施
  -> 强制措施
  -> 移送审查起诉 / 撤案 / 调解
```

每个流程节点可以挂接“应有材料”：

- 接警：接警记录、警情流转日志、受案登记表
- 伤情判断：鉴定意见、送检记录、鉴定通知书
- 撤案/调解：撤案审批、调解协议、释放依据、审批流日志

这类流程知识不属于单个案件，而属于系统级可成长知识库。

## 12. 句级溯源设计

系统的一个核心目标是“每句话都能回到证据”。

当前溯源对象包括：

- passage
- 证据文件
- 图谱路径
- PPR 检索结果
- 规则 finding

理想链路：

```text
报告句子
  -> 支撑 passage
  -> 所属文件
  -> 文件 proof_purpose / process_stage
  -> 原始图谱路径
```

若某句话没有可靠支撑，应当：

- 标记为未证实
- 降低可信度
- 不作为 finding 支撑
- 必要时要求模型重写

## 13. 人工干预与可审计性

系统保留人工介入能力，主要包括：

- 图谱节点新增
- 图谱关系新增
- 节点/关系删除
- 节点/关系更新
- 标记已核验
- 采纳疑点候选
- 后续规则反馈

这点很重要，因为检察场景不能完全自动化。模型只能给建议，最终证据审查、事实认定和法律定性需要人工确认。

## 14. 当前项目的技术特点

### 14.1 图谱与 RAG 混合

项目不是简单聊天机器人，而是把 RAG、知识图谱、规则包和证据地图结合起来。

核心优势：

- 可以多跳检索
- 可以回到证据原文
- 可以显示实体关系
- 可以通过规则发现材料缺口
- 可以对分析结论做溯源

### 14.2 多分辨率证据组织

系统不再只依赖一个超大原始图，而是逐渐形成三层结构：

```text
文件层：证据边界
片段层：原文 passage
原始图谱层：实体关系
```

这种设计更适合法律证据场景，因为法律材料天然以“文件”为边界。

### 14.3 规则和模型分工

系统不把所有判断都交给 LLM。

更合理的分工是：

```text
规则包：发现结构性问题
图谱：提供关系路径
HippoRAG：召回多跳证据
DeepSeek：组织语言和解释
人工：最终确认
```

### 14.4 可成长法律知识库

法律知识、流程规则、罪名模板和用户上传材料都可以逐步扩展。系统会越来越像一个面向检察工作的“办案知识底座”。

### 14.5 本地化与可部署性

当前系统以本地运行机器为主要存储和服务环境，适合课程项目、内网演示和小规模部署。

前端可通过 Vite 开发服务器运行，也可以 build 后由 Caddy 挂载到指定路径，如：

```text
https://adm143.xyz/jcmx
```

## 15. 当前仍需改进的问题

项目还在快速迭代，主要问题包括：

- OpenIE 对中文法律文本仍不稳定
- 实体类型和关系类型仍需更强约束
- 普通非结构化边的时间戳仍不完整
- 别名/马甲账户合并建议还未成熟
- 报告句子与 passage 的生成时绑定仍需加强
- 文件层、片段层和原始图谱层的视觉体验还在打磨
- DeepSeek agentic RAG 还没有完全达到真正动态规划
- 法律知识库和规则包需要更多专家知识填充

这些问题并不影响当前系统作为“证据组织与智能分析原型”的价值，但需要在后续版本继续推进。

## 16. 一句话总结

本项目的特点是：以证据为中心，用文件层保留边界，用 passage 层连接原文，用原始图谱层承载事实关系，用 HippoRAG 做多跳检索，用规则包发现办案缺口，用 DeepSeek 生成可溯源的分析文本，最终让检察官在一个工作台里完成证据导入、图谱查看、事实画像、疑点分析和报告生成。
