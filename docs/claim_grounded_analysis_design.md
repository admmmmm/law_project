# 逐句可溯源分析设计

## 目标

当前系统的问题不是单纯的页面问题，而是分析结果没有成为“可验证的办案结论”。目标是让 DeepSeek Pro 基于三类材料生成分析：

- 证据数据库：案件证据原文、结构化流水、通话记录、人工确认记忆。
- 法律数据库：法律条文、立案标准、司法解释、证据标准、分罪名要件模板。
- 办案模板：主体要件、客观行为、主观方面、结果因果、反侦察行为、证据缺口、抗辩预判。

最后输出的不是一整段自由文本，而是一组“可验证句子 claim”。每一句都必须能点开，看到对应证据原文、PPR passage、路径和校验状态。

## 核心原则

1. 模型可以生成分析，但不能单独决定事实成立。
2. 每一句结论都必须绑定证据 passage。
3. 没有可靠证据的句子不能作为正式结论，只能进入“待核查/需补证/模型重写”状态。
4. 法律要件是组织分析的骨架，图谱和 RAG 是找证据的工具。
5. 反侦察行为必须作为单独任务识别，不能只依赖普通实体关系图。

## 推荐数据结构

画像分析接口应返回结构化结果，而不是简单 Markdown：

```json
{
  "section": "主体要件",
  "claims": [
    {
      "claim_id": "claim_001",
      "text": "杨周武案发时担任同乐派出所所长。",
      "element": "主体要件.司法工作人员身份",
      "status": "supported",
      "confidence": 0.86,
      "supporting_passages": [
        {
          "evidence_id": "evd_xxx",
          "evidence_title": "深圳市人民检察院立案决定书",
          "passage": "杨周武，男，同乐派出所所长...",
          "score": 0.91
        }
      ],
      "graph_paths": [
        "杨周武 --任职--> 同乐派出所"
      ],
      "verification_notes": "人名、职务、单位均能在证据原文中对应。"
    }
  ]
}
```

## 生成流程

### 1. 证据预处理

证据导入后先生成短 passage：

- 非结构化证据：按句子、条款、表格行切分。
- 结构化流水：一行一 passage，必要时按主体聚合生成“可读摘要 passage”。
- 通话记录：一组高频联系人或关键时间窗口生成一条 passage。

passage 应尽量短，建议 120 到 220 字。太长会导致点击一句话后右侧证据不聚焦。

### 2. 要件模板加载

创建案件时选择罪名，例如“徇私枉法罪”，系统加载模板：

- 主体要件：司法工作人员身份、职务权限、经办范围。
- 客观行为：对明知有罪的人故意包庇，或者使其不受追诉。
- 主观方面：明知、故意、徇私动机。
- 结果因果：错误处置、逃避追诉、被害人权益受损、社会危害后果。
- 反侦察/规避留痕：现金化、白手套、马甲账户、绕开正式程序、倒签补录、模糊备注、删除或补造文书。

### 3. 召回证据

每个要件生成若干检索问题，例如：

```text
杨周武 是否担任同乐派出所所长 职务权限 证据
王静 何晓初 杨周武 请托 收钱 调解
拘留 释放 调解 撤销案件 杨周武 刘力飚
现金 取现 存入 白手套 马甲账户
```

系统使用 HippoRAG/PPR 从证据库中召回 passage，并带上证据 ID、分数、路径。

### 4. DeepSeek Pro 生成 claim

DeepSeek Pro 不直接写长报告，而是按模板输出 JSON claim：

- 只允许基于给定 passage 和法律模板作答。
- 每个 claim 必须列出候选 evidence_id 或 passage 编号。
- 不确定的地方必须写成“尚不能确认”“仍需补证”，不能编。

### 5. 逐句校验

系统对每条 claim 做二次校验：

- 证据校验：claim 中的关键实体是否出现在 supporting passages。
- 时间校验：claim 时间是否能与证据时间、流水时间、通话时间对上。
- 金额校验：金额是否能从流水或证言中找到。
- 法律要件校验：claim 是否对应一个明确要件。
- PPR 校验：相关 passage 分数是否超过阈值。

校验结果：

- `supported`：证据充分，可以展示为正常结论。
- `weak`：有相关证据但不够直接，展示为黄色待核查。
- `unsupported`：没有可靠证据，标红，不进入正式结论。
- `conflict`：存在相互冲突证据，进入人工复核。

### 6. 幻觉处理

幻觉在原理上是可能出现的。处理方式不应该只是相信模型，而是做“生成后验证”。

如果 claim 没有可靠证据：

1. 第一次：自动打回 DeepSeek Pro，要求基于已召回 passage 改写。
2. 第二次仍失败：把 claim 降级为“待核查问题”。
3. 前端显示：红色标记“未找到可靠证据”，并展示模型原句、检索结果和建议补证方向。
4. 人工可以选择：删除、改写、标记为调查员线索、加入记忆但不入正式报告。

## 反侦察识别

反侦察操作不能只靠普通三元组抽取。需要单独模板：

### 资金反侦察

- 大额款拆成小额转账。
- 备注写成借款、货款、还款、劳务费。
- 先 ATM 取现，后现金存入。
- 白手套账户、亲属账户、马甲账户过桥。

### 程序反侦察

- 倒签、补录、后补审批。
- 以调解掩盖刑事追诉。
- 文书名称与真实处置不一致。
- 关键节点没有正式审批或记录缺失。

### 关系反侦察

- 不直接联系，由配偶、下属、熟人转达。
- 高频通话出现在处置节点前后。
- 表面无资金关系，但有宴请、请托、第三方转账。

这些识别结果也应输出 claim，并经过同样的证据校验。

## 前端交互

前端不再渲染一整段“模型报告”，而是渲染 claim 列表：

- hover：只高亮当前句。
- click：只打开当前句的证据详情。
- supported：正常显示。
- weak：黄色边框。
- unsupported：红色边框，提示“未证实”。
- conflict：紫色或橙色，提示“证据冲突”。

右侧抽屉显示：

- 当前 claim。
- 证据原文 passage。
- PPR 分数。
- 图谱路径。
- 法律要件。
- 校验状态。
- 如果失败，显示“打回重写/转为待核查/人工确认”按钮。

## 与阿加莎文本场景的关系

如果把一本侦探小说前几章作为材料导入，本系统也应该能工作。区别只是法律数据库权重降低，案件模板换成“叙事侦查模板”：

- 人物关系。
- 时间线。
- 行为轨迹。
- 动机与机会。
- 证词矛盾。
- 反侦察或误导行为。
- 可疑信息。
- 仍缺失的信息。

本质仍然是：文本切 passage -> 建人物/事件/线索图 -> 模型生成 claim -> 每个 claim 回到原文证据。
