# 检察侦查画像模型：系统架构、技术路径与功能成果

## 一、系统整体架构图

本系统面向检察侦查办案场景，围绕“证据接入、图谱建模、智能检索、事实画像、疑点分析、法律知识支撑”构建一套可溯源、可审查、可迭代的智能分析平台。

整体架构如下：

```text
┌────────────────────────────────────────────────────────────┐
│                        前端交互层                           │
│                                                            │
│  案件导入  案件证据地图  画像报告  智能分析  RAG 对话        │
│  检察技能库  法律知识库  分析上下文调试  原始图谱维护        │
└──────────────────────────────┬─────────────────────────────┘
                               │ REST API
┌──────────────────────────────▼─────────────────────────────┐
│                        后端服务层                           │
│                                                            │
│  FastAPI / Pydantic / SQLite / 本地文件存储                 │
│                                                            │
│  案件管理服务  证据导入服务  图谱服务  画像服务              │
│  智能分析服务  RAG 检索服务  检察技能包服务                  │
│  法律知识服务  分析上下文与溯源服务                          │
└──────────────────────────────┬─────────────────────────────┘
                               │
┌──────────────────────────────▼─────────────────────────────┐
│                  数据处理与智能分析层                       │
│                                                            │
│  结构化数据解析       非结构化证据切分       OpenIE 抽取     │
│  EvidenceMap 证据地图 HippoRAG 多跳检索     DeepSeek 生成    │
│  Agentic RAG 检索计划 检察技能包规则执行     句级溯源校验     │
└──────────────────────────────┬─────────────────────────────┘
                               │
┌──────────────────────────────▼─────────────────────────────┐
│                    证据与知识底座                           │
│                                                            │
│  案件证据库：证据文档、银行流水、通话短信、结构化表格        │
│  证据图谱库：实体、关系、时间、来源、人工修正记录            │
│  RAG 索引库：passage、embedding、HippoRAG PPR 路径           │
│  法律知识库：罪名模板、构成要件、办案流程、证据标准          │
│  检察技能库：规则包、检查项、finding、回放与反馈             │
└────────────────────────────────────────────────────────────┘
```

该架构的核心思想是：先把案件材料转化为可检索、可关联、可溯源的数据底座，再让大模型在证据与法律知识约束下进行分析，而不是直接把全部原文塞给模型自由生成。

## 二、技术解决路径

### 1. 解决案件材料复杂、来源多样的问题

检察案件材料通常包含文书、笔录、银行流水、通话记录、短信、表格、压缩包等多种形态。系统采用“统一导入、分类处理”的方式，将不同来源的材料归入同一案件空间。

技术路径：

- 对文件夹和压缩包进行批量接入。
- 对 Markdown、TXT、PDF、DOCX 等材料进行文本化处理。
- 对 CSV/XLSX 等结构化材料进行字段解析。
- 将证据材料统一登记为 EvidenceRecord，保留文件名、来源路径、证据类型、形成时间、案情时间等元数据。

这样做的价值是：系统不只保存“文件”，而是保存“可被后续分析使用的证据对象”。

### 2. 解决非结构化证据难以计算的问题

对于笔录、决定书、报告、专报等非结构化文本，系统不直接整篇送入分析，而是先切分为 passage，并通过 OpenIE 抽取人物、机构、行为、文书、金额、时间等事实关系。

技术路径：

- 将原始证据切分为较短 passage。
- 使用大模型进行命名实体识别和关系抽取。
- 将抽取结果转化为图谱中的节点和边。
- 每条边保留来源证据和 passage 引用。

这样做的价值是：证据中的自然语言事实可以进入图谱、检索和溯源链条。

### 3. 解决结构化流水与案件事实对齐的问题

银行流水、通话记录、短信记录属于高价值结构化材料，但如果直接进入图谱会造成节点爆炸、重复边和无意义噪声。系统采用“结构化解析优先、聚合入图”的方式。

技术路径：

- 对银行流水识别交易双方、金额、时间、备注、账户别名。
- 对通话记录识别主叫、被叫、通话时间、持续时间、对应真实身份。
- 对同一主体之间的重复流水进行聚合。
- 对结构化事实保留精确字段，不依赖 OpenIE 二次猜测。

这样做的价值是：资金链、通话链能够作为客观线索进入图谱，同时减少无效节点和边。

### 4. 解决图谱过大、难以观察的问题

原始图谱包含人物、机构、文书、金额、时间、行为等大量节点，直接展示会造成线条密集、节点重叠、用户难以理解。系统引入“案件证据地图”作为图谱页默认视图。

技术路径：

- 文件层：每份证据作为一个文件节点，展示证据版图。
- 片段层：展示证据文件下的 passage 片段。
- 原始图谱层：保留原先完整图谱，用于细粒度维护和调试。
- 通过层级切换和展开机制，让用户从全局逐步进入细节。

这样做的价值是：用户可以先看“证据结构”，再看“原文片段”，最后看“事实关系”，避免一上来被细碎节点淹没。

### 5. 解决普通 RAG 只会相似检索、不擅长多跳关联的问题

案件分析往往不是找一段最相似文本，而是要跨证据发现人物关系、资金链、通话链、时间链和文书链。因此系统接入 HippoRAG，利用图结构和 PPR 检索实现多跳召回。

技术路径：

- 将 passage 与实体、三元组建立关联。
- 查询时以问题或实体作为种子。
- 使用 Personalized PageRank 在图上扩散。
- 返回相关 passage、路径和图谱事实。

这样做的价值是：系统可以从“杨周武”扩展到“王静、何晓初、刘力飚、调解、释放、资金”等关联线索，而不是只匹配关键词。

### 6. 解决大模型幻觉和报告不可审查的问题

检察场景不能接受无依据的自然语言结论。系统通过句级溯源、证据绑定和可信度分级降低幻觉风险。

技术路径：

- DeepSeek 输出的分析文本按句切分。
- 每一句话都尝试绑定 passage、证据文件或图谱路径。
- 有可靠证据支撑的句子显示为强/中/弱支撑。
- 找不到可靠证据的句子标记为暂无支撑，不能作为确定结论。
- 前端点击句子可打开右侧溯源面板，查看原文和检索路径。

这样做的价值是：报告不是“模型说了算”，而是“模型生成、证据校验、人工审查”。

### 7. 解决法律知识与案件分析脱节的问题

本项目不是通用问答系统，而是检察办案辅助系统。因此系统增加法律知识库和检察技能库。

技术路径：

- 法律知识库保存罪名模板、构成要件、办案流程、应有材料、证据标准、法条和司法解释。
- 检察技能库保存可运行的规则包，例如材料完整性、程序转向、权限控制。
- 智能分析时可以调用法律知识和规则包，形成“要查什么、缺什么、下一步做什么”的框架。

这样做的价值是：系统不只是总结证据，还能按检察办案逻辑提示证据缺口和核查方向。

## 三、功能实现成果清单

### 1. 案件管理与数据导入

已实现内容：

- 支持创建案件、切换案件、删除案件。
- 支持文件夹和压缩包导入。
- 支持 Markdown、TXT、CSV、XLSX、JSON、PDF、DOCX 等格式接入。
- 支持案件数据保存在运行机器本地，避免切页后状态丢失。
- 支持自定义案件入口。

实现价值：

案件材料可以按案件隔离管理，满足多案件工作台的基本要求。

### 2. 证据处理与结构化清洗

已实现内容：

- 将证据文档拆分为独立 evidence_docs。
- 生成结构化银行流水、通话记录、案情梳理数据。
- 对银行流水中的假名与真实人物进行映射。
- 对通话记录、银行流水与案情时间进行对齐。
- 支持 evidence、structured、legal knowledge 等目录化组织。

实现价值：

系统具备从原始材料到分析数据的处理链路，为后续图谱和 RAG 提供数据基础。

### 3. 原始证据图谱

已实现内容：

- 支持从非结构化证据中抽取人物、机构、文书、行为、金额、时间等节点。
- 支持从结构化流水中抽取交易关系、通话关系。
- 支持节点和边的展示、筛选、详情查看。
- 支持图谱人工增删改查。
- 支持时间轴过滤和图谱布局切换。

实现价值：

形成案件的事实关系网络，为人物关系、行为链、资金链和证据溯源提供基础。

### 4. 案件证据地图

已实现内容：

- 图谱页默认展示“案件证据地图”。
- 支持文件层、片段层、原始图谱层三层视图。
- 文件层用于展示证据文件之间的整体结构。
- 片段层用于观察 HippoRAG passage 级证据片段。
- 原始图谱层保留完整图谱维护能力。

实现价值：

解决原始图谱过于复杂的问题，让用户像看地图一样从证据文件逐层进入细节。

### 5. HippoRAG 检索与 RAG 对话

已实现内容：

- 接入 BGE-M3 embedding 模型。
- 接入 HippoRAG 检索链路。
- 支持基于案件证据进行 RAG 问答。
- 支持返回 passage、检索分数和部分路径信息。
- 支持 RAG 对话页面。

实现价值：

系统具备基于案件材料的问答能力，并能通过多跳检索提升关联召回能力。

### 6. Agentic RAG 检索计划器

已实现内容：

- 引入检索计划器思想。
- 将文档检索、图谱检索、节点扩展、时间检索、法律知识检索封装为内部工具。
- 支持多轮检索、工具调用记录和检索摘要。
- 智能分析和画像报告可显示本轮调用了哪些检索能力。

实现价值：

从“固定 query 检索”逐步升级为“围绕问题动态检索”，为后续更强的多轮分析打基础。

### 7. 画像报告页

已实现内容：

- 支持生成事实画像和详细画像报告。
- 支持人物关系、行为还原、要件核查、缺口提示、抗辩预判等内容框架。
- 支持报告句子级点击溯源。
- 支持显示证据原文和 HippoRAG PPR 检索结果。
- 支持报告结果持久化，避免切页后重复生成。

实现价值：

画像页承担“把案件事实讲清楚”的任务，面向检察官形成可审查的事实画像。

### 8. 智能分析页

已实现内容：

- 支持假设验证。
- 支持可疑资金流分析。
- 支持多轮对话式分析。
- 支持分析会话卡片保存、打开、删除。
- 支持针对某份证据进行追问。
- 支持答案 Markdown 渲染和句级溯源。

实现价值：

智能分析页承担“发现疑点、验证假设、提出核查方向”的任务，区别于画像页的事实还原。

### 9. 检察技能库

已规划/部分实现内容：

- 技能包列表。
- 技能包详情。
- 规则检查项。
- 测试与回放。
- 导入、导出、发布入口。
- 预留材料完整性、程序转向、权限控制等规则包。

实现价值：

将检察经验沉淀为可运行、可测试、可迭代的技能包，使系统越用越接近办案逻辑。

### 10. 法律知识库

已规划/部分实现内容：

- 罪名模板。
- 办案流程。
- 应有材料清单。
- 证据标准。
- 法条和司法解释。
- 上传知识材料入口。

实现价值：

为案件分析提供法律先验，避免系统只看事实材料而缺少办案规范和构成要件框架。

### 11. 分析上下文调试页

已规划内容：

- 展示 EvidenceMap documents/passages/triples。
- 展示 RuleFindings。
- 展示 HippoRAG passages/paths。

实现价值：

为开发和答辩提供可解释性入口，说明一次分析到底用了哪些证据、规则和检索结果。

## 四、踩分点一：画像层

画像层的目标不是简单生成一段总结，而是围绕检察办案视角回答：

```text
这个人是谁？
他有什么职权？
他和谁有关？
他做了什么？
这些行为由哪些证据支撑？
还有哪些证据缺口？
```

画像层可以拆成三层：

### 1. 基础信息聚合

内容包括：

- 嫌疑人身份。
- 任职单位。
- 职务权限。
- 与关键人物、机构、账户的关系。
- 涉案证据数量和来源。

作用：

解决主体身份和职权基础问题。

### 2. 行为事实还原

内容包括：

- 按时间线还原关键事件。
- 展示请托、收钱、指派、调解、释放、报告、事故后果等行为链。
- 将资金流水、通话记录、文书审批和证人证言放到同一事实链中。

作用：

解决“嫌疑人到底做了什么”的问题。

### 3. 要件核查与证据归类

内容包括：

- 主体要件。
- 客观行为。
- 主观方面。
- 结果与因果。
- 证据支撑强弱。
- 缺口标红。
- 抗辩预判。

作用：

把普通案件事实转化为检察办案可使用的要件化审查材料。

画像层的核心踩分点在于：系统不是泛泛地“写报告”，而是用证据图谱、RAG 检索和法律模板共同生成可溯源的人物画像。

## 五、踩分点二：分析层

分析层的目标不是复述事实，而是帮助检察官发现值得继续调查的问题。

分析层可以包括三个方向：

### 1. 假设验证

检察官可以输入一个假设，例如：

```text
杨周武是否可能通过审批权改变案件处理结果？
是否存在文书补录、倒签、隐瞒、程序转向？
```

系统通过 RAG、图谱和法律知识多轮检索，返回：

- 支持该假设的证据。
- 反驳或不足的证据。
- 目前无法确认的部分。
- 下一步应调取的材料。

### 2. 可疑资金流分析

系统围绕银行流水、现金取存、过桥账户、马甲账户、赔偿款等线索进行分析。

重点不是直接定性，而是提示：

- 是否存在多跳资金路径。
- 是否存在取现后现金存入。
- 是否存在白手套账户。
- 是否与关键案件处置节点时间接近。
- 是否需要进一步调取银行凭证或监控。

### 3. 证据碰撞与规则发现

系统将文书、笔录、流水、通话、法律流程放在一起碰撞，发现：

- 刑事立案后调解结案。
- 拘留后释放依据不明。
- 伤情鉴定或送检材料缺失。
- 审批人同时是被调查对象。
- 资金、通话和文书时间节点相互靠近。

分析层的核心踩分点在于：它不把模型结论直接当事实，而是把模型作为“提出疑点、组织证据、建议核查”的工具。

## 六、总结

本项目的创新点在于将“证据图谱 + HippoRAG 多跳检索 + DeepSeek 生成 + 检察规则包 + 法律知识库”组合成一个面向检察侦查的智能办案原型。

它不是普通聊天机器人，也不是单纯的知识图谱展示工具，而是围绕检察官的实际工作流设计：

```text
导入证据
  → 清洗和结构化
  → 建立证据图谱
  → 多跳检索关联证据
  → 生成事实画像
  → 发现疑点并验证假设
  → 输出可溯源报告和核查建议
```

系统目前已经形成从数据接入到图谱、RAG、画像、分析、法律知识和技能规则的完整技术闭环。后续重点应继续提升三方面能力：

1. 图谱质量：更准确的实体类型、关系类型、时间戳和别名合并建议。
2. 分析质量：更成熟的 Agentic RAG 和检察技能包规则体系。
3. 溯源质量：让每一句结论都能稳定回到证据原文、图谱路径和法律依据。
