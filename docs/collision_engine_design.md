# 分析碰撞引擎设计

## 1. 目标

“碰撞引擎”不是直接替检察官下结论，而是做三件事：

1. **提出假设**：从证据、图谱、RAG 结果中生成可检验的侦查假设。
2. **试图验证**：用图操作、证据片段、三元组路径去支持或反驳假设。
3. **写入假设池**：如果没有被图谱和证据严重违反，就把假设作为“待核查线索”保存，附上支持、反证、缺口和下一步建议。

最终页面不应显示“模型说了什么”，而应显示：

```text
假设：王静通过何晓初向杨周武请托，并以资金利益影响案件处置。
状态：可成立，仍需补强
支持：短信、询问笔录、通话、资金流水、释放/调解文书
反证：暂无直接反证；缺少任职权限、人事档案、现金交接直接证据
下一步：调取杨周武任职文件、何晓初账户完整流水、停车场/场所监控
```

## 2. 核心概念

### 2.1 假设 Hypothesis

假设是一个结构化对象，不是一段自由文本。

```json
{
  "hypothesis_id": "hyp_xxx",
  "title": "王静通过何晓初向杨周武请托",
  "type": "request_chain",
  "claim": "王静可能通过何晓初向杨周武请托，并影响故意伤害案处置。",
  "focus_entities": ["王静", "何晓初", "杨周武"],
  "expected_patterns": ["请托链", "亲属/中间人", "资金利益", "处置异常"],
  "status": "plausible",
  "confidence": 0.72,
  "support": [],
  "contradictions": [],
  "gaps": [],
  "next_steps": []
}
```

### 2.2 验证 Evidence Test

验证不是一次 LLM 判断，而是一组图和证据测试：

- 路径测试：图上能否找到关键实体之间的路径。
- 时间测试：事件顺序是否可能成立。
- 类型测试：关系类型是否符合该假设的模式。
- 证据测试：路径上的边是否能回到证据原文。
- 反证测试：是否存在强烈冲突，如时间倒置、主体不相干、同一金额不闭合。

### 2.3 写入原则

只有满足下面条件才写入假设池：

- 至少有 2 类来源支撑，例如 passage + triple、文书 + 通话、资金 + 证言。
- 没有严重图谱冲突。
- 能明确列出缺口和下一步验证方式。

如果只有一个弱关键词命中，不写入，只作为临时候选。

## 3. 三种推理如何落地

### 3.1 Induction 归纳

从多个事实中归纳出模式。

例子：

```text
王静 -> 通话 -> 何晓初
何晓初 -> 通话 -> 杨周武
王静 -> 转账/取现 -> 资金对象
杨周武 -> 批准 -> 调解结案/释放
```

归纳出的假设：

```text
王静可能通过何晓初影响杨周武处置案件。
```

工程实现：

1. 扫描图中高频实体和高权重边。
2. 找到“多类边汇聚”的局部子图：
   - 通话/短信
   - 资金
   - 请托/承诺
   - 批准/释放/调解
3. 生成模式候选。

适合发现：

- 请托链
- 资金链
- 白手套/马甲账户
- 程序异常
- 权力处置链

### 3.2 Deduction 演绎

从法律要件和办案模板出发，检查当前事实是否满足。

例子：

徇私枉法罪模板：

```text
主体：司法工作人员
行为：明知有罪而使其不受追诉
主观：徇私、故意
结果：案件被撤销、调解、释放、未追诉
```

演绎测试：

```text
如果假设“杨周武构成徇私枉法”成立，
则图谱中应能找到：
1. 杨周武具有职务/审批/指派权
2. 原案具有应追诉事实
3. 杨周武介入或批准异常处置
4. 处置结果是释放/调解/撤案
5. 存在请托、收钱、明知等主观证明入口
```

工程实现：

1. 加载法律知识库和罪名模板。
2. 把模板拆成若干 required slots。
3. 对每个 slot 发起图查询和 RAG 查询。
4. 得到：
   - 已支持
   - 弱支持
   - 缺口
   - 冲突

适合做：

- 要件核查
- 证据缺口
- 抗辩预判
- 报告结构化输出

### 3.3 Abduction 溯因

从异常结果倒推最可能解释。

例子：

观察到：

```text
刑事拘留 -> 调解结案 -> 释放
同时出现请托、通话、资金流
```

可解释假设：

```text
存在外部请托和利益输送，导致案件被异常调解处理。
```

工程实现：

1. 先定义“异常观察”：
   - 本应追诉却调解/释放
   - 资金发生在处置前后
   - 通话密集发生在关键节点前后
   - 文书审批链异常
2. 对每个异常观察生成解释候选。
3. 用图路径和 passage 验证候选解释是否覆盖异常。

适合发现：

- 反侦察行为
- 异常资金闭环
- 程序规避
- 关键中间人

## 4. 图操作

碰撞引擎依赖的图操作应独立成 `GraphReasoner`。

### 4.1 邻域扩展

```python
expand_neighbors(seed_entities, depth=1|2, relation_filter=None)
```

用途：

- 从嫌疑人向外扩展人物关系。
- 从资金节点向外找白手套。
- 从文书节点向外找审批人。

### 4.2 路径搜索

```python
find_paths(source, target, max_hops=3, relation_filter=None)
```

用途：

- `王静 -> 何晓初 -> 杨周武`
- `杨周武 -> 刘力飚 -> 调解/释放`
- `资金账户 -> 过桥人 -> 收款人`

### 4.3 时间窗口碰撞

```python
temporal_join(events_a, events_b, window_days=3|7|30)
```

用途：

- 通话是否发生在转账前后。
- 请托是否发生在释放/调解前。
- 资金是否发生在关键文书前后。

### 4.4 子图打包

```python
build_subgraph_context(paths, edges, passages)
```

输出给 DeepSeek：

```json
{
  "subgraph": [
    {"source": "王静", "relation": "通话", "target": "何晓初", "time": "..."},
    {"source": "何晓初", "relation": "通话", "target": "杨周武", "time": "..."},
    {"source": "杨周武", "relation": "批准", "target": "释放"}
  ],
  "passages": [...]
}
```

## 5. DeepSeek 在引擎里的位置

DeepSeek 不负责凭空决定真假。它负责三件事：

1. **生成候选假设**  
   输入：局部子图、passage、法律模板。  
   输出：若干可检验假设。

2. **解释验证结果**  
   输入：图操作返回的支持/冲突/缺口。  
   输出：自然语言说明。

3. **提出下一步查询**  
   输出 `next_queries`，后端再调用 HippoRAG 检索。

不要让 DeepSeek 直接说“成立/不成立”而没有证据绑定。

## 6. 多轮工作流

第一版可以这样做：

### Round 1：提出假设

输入：

- 立案文书
- 嫌疑人中心 2-hop 子图
- 高分 RAG passage
- 法律模板

DeepSeek 输出：

```json
{
  "hypotheses": [
    {
      "title": "王静通过何晓初向杨周武请托",
      "type": "request_chain",
      "focus_entities": ["王静", "何晓初", "杨周武"],
      "expected_patterns": ["请托", "通话", "资金", "异常处置"],
      "why": "现有材料中出现王静、何晓初、杨周武之间的联系和收钱表述。"
    }
  ],
  "next_queries": [
    "王静 何晓初 杨周武 请托 3万元",
    "杨周武 刘力飚 指派 调解",
    "故意伤害案 调解结案 释放"
  ]
}
```

### Round 2：检索验证

后端执行：

- HippoRAG retrieve
- graph path search
- temporal join
- contradiction check

输出验证包：

```json
{
  "support": [...],
  "contradictions": [...],
  "gaps": [...],
  "paths": [...]
}
```

### Round 3：形成假设记录

DeepSeek 只负责整理：

```json
{
  "status": "plausible",
  "confidence": 0.72,
  "summary": "现有证据支持该请托链条的基本结构，但现金交接仍需补强。",
  "next_steps": [...]
}
```

后端负责保存。

## 7. 状态机

建议假设状态：

```text
candidate   候选，只有弱信号
plausible   可成立，未见严重冲突
supported   多源支撑，适合进入报告
conflicted  存在关键冲突
rejected    被明确反证排除
```

## 8. 严重违反图谱的标准

“没有严重违反图谱”不是“完全证明”。严重违反包括：

- 时间顺序不可能：收钱晚于所有处置动作很久，且无补充解释。
- 主体不可能：假设中的人未出现在任何证据或图谱路径。
- 关系断裂：关键实体之间无 passage、无路径、无共同证据。
- 金额矛盾：同一笔资金金额、方向、主体完全冲突。
- 法律模板冲突：缺少基本主体身份或案件处置对象。

只要不是严重违反，就可以进入 `plausible` 或 `candidate`，但必须标明缺口。

## 9. 第一版实现范围

第一版只做 3 类假设：

1. **请托链假设**
   - 王静/何晓初/杨周武/刘力飚
   - 通话、证言、短信、调解处置

2. **资金利益链假设**
   - 王静 -> 过桥人 -> 何晓初/杨周武
   - ATM 取现 / 现金柜台存入
   - 处置节点前后时间窗口

3. **异常处置链假设**
   - 故意伤害案立案/拘留
   - 调解结案/释放
   - 杨周武批准/指派/安排

不要一开始做“所有反侦察”。反侦察可以先作为 abduction 的异常观察。

## 10. 后端接口建议

### 10.1 运行碰撞分析

```http
POST /api/v1/cases/{case_id}/analysis/collision/run
```

请求：

```json
{
  "focus_person": "杨周武",
  "hypothesis_types": ["request_chain", "fund_chain", "procedure_anomaly"],
  "max_rounds": 3
}
```

返回：

```json
{
  "case_id": "case_xxx",
  "hypotheses": [...],
  "rounds": [
    {
      "round": 1,
      "action": "generate_hypotheses",
      "llm_context_id": "..."
    },
    {
      "round": 2,
      "action": "verify_graph",
      "paths_checked": 12,
      "passages_checked": 40
    }
  ]
}
```

### 10.2 保存假设

假设可以先存在 sqlite `memories` 或新增 `hypotheses` 表。建议新增表，避免和记忆混在一起。

```text
hypotheses
- case_id
- hypothesis_id
- payload
- created_at
- updated_at
```

## 11. 与当前系统的关系

当前已有能力：

- HippoRAG retrieve：负责 passage 召回。
- graph：负责结构化关系。
- portrait facts：已有文段式 DeepSeek 输出和溯源。

碰撞引擎应复用它们，但不要塞进画像页。

推荐页面：

```text
智能分析
  - 人物关系画像
  - 行为还原
  - 碰撞假设
    - 假设池
    - 支持证据
    - 反证/缺口
    - 下一步查询
```

## 12. 最小可用版本

MVP 只做：

1. 后端固定生成 3 个假设候选。
2. 对每个假设执行：
   - 2-hop 子图
   - 3 个 HippoRAG 查询
   - 简单时间窗口碰撞
3. DeepSeek 整理成假设记录。
4. 页面显示假设、支持、缺口、下一步。

这已经足够体现“提出假设 -> 试图验证 -> 没有严重违反则写下来”的闭环。
