# 参考 MiroFish 的处理层设计

## 1. 这份文档讨论什么

这份文档只讨论项目的**处理层**。  
这里的处理层，指的是从原始证据数据进入系统，到形成可用图谱底座的全过程。

我们把处理层收缩成三步：

1. **解析证据**
2. **生成领域本体**
3. **图谱构建**

这三步做完，才能进入后面的分析层和碰撞层。

## 2. 总体认识

参考 `MiroFish`，我们不应把“图谱”理解为一个展示页面，而应把它理解为处理层的产物。  
也就是说，处理层真正要解决的问题是：

- 原始材料很乱，怎么变成可计算数据
- 场景对象很多，怎么统一定义
- 人、案、钱、行为之间的关系，怎么稳定落到结构化图谱里

所以处理层的目标可以压缩成一句话：

**把依法调取的多源证据数据，转成统一语义、统一结构、统一关系的侦查图谱。**

## 3. 第一步：解析证据

## 3.1 这一步要做什么

这一步解决的是“原始数据怎么进系统”的问题。  
题目明确提到海量、多格式电子数据，所以这里不能只支持单一文本。

解析证据的目标不是直接下结论，而是把各种证据材料统一变成系统能继续处理的中间数据。

## 3.2 我们的设计思路

输入数据至少分为两类：

### 第一类：非结构化材料

- PDF
- Word
- TXT
- OCR 后的文本
- 案卷材料
- 说明材料
- 笔录
- 文书

这类数据的处理目标是：

- 提取文本
- 清洗格式
- 分段切块
- 标注来源

### 第二类：结构化或半结构化数据

- Excel
- CSV
- 银行流水
- 通联记录
- 出入记录
- 操作日志

这类数据的处理目标是：

- 读取字段
- 字段标准化
- 时间格式统一
- 人员、账户、事件字段归一

所以这一层不只是“读文件”，而是要做一个**证据接入与标准化模块**。

## 3.3 可以参考 MiroFish 的什么

`MiroFish` 已经做了基础文件解析和文本预处理：

- [file_parser.py](</c:/Users/adm14/Desktop/law_project/MiroFish/backend/app/utils/file_parser.py>)
- [text_processor.py](</c:/Users/adm14/Desktop/law_project/MiroFish/backend/app/services/text_processor.py>)

它目前已经具备：

- PDF / Markdown / TXT 的文本提取
- 编码兜底
- 文本清洗
- 长文本切块

这说明它已经给了我们一个基础版本的“非结构化文本接入层”。

## 3.4 我们需要补哪些技术

如果面向我们的题目，至少还要补：

- `python-docx`：处理 Word
- `pandas` / `openpyxl`：处理 Excel / CSV
- `PyMuPDF`：处理 PDF
- OCR 接口或离线 OCR：处理扫描件图片

对日志和流水类数据，还需要增加：

- 字段映射规则
- 时间字段归一化
- 身份字段归一化
- 账户字段归一化

## 3.5 能不能做到

**能做到，而且实现难度是处理层里最低的一段。**

原因是：

- 文件读取是成熟问题
- 文本清洗和切块是成熟问题
- 表格解析和字段归一化也是成熟问题

真正的难点不在“能不能读出来”，而在“读出来以后如何统一成侦查场景可用的数据对象”。  
但这已经属于第二步和第三步的问题。

## 3.6 这一步的产出是什么

这一步做完后，应该产出两类中间结果：

### 文本中间结果

- 文档编号
- 原始来源
- 提取文本
- 文本块列表

### 结构化中间结果

- 标准化表格记录
- 统一字段名
- 统一时间格式
- 统一对象标识

一句话说，这一步产出的是：

**可继续抽取实体和关系的标准化证据数据。**

## 4. 第二步：生成领域本体

## 4.1 这一步要做什么

这一步解决的是“我们到底要抽什么”的问题。  
如果没有领域本体，后面实体抽取、关系构建、图谱查询都会失控。

领域本体本质上要回答两个问题：

- 本项目里有哪些核心对象
- 这些对象之间可能有哪些关系

## 4.2 我们的设计思路

这里要特别考虑题目的前提是**已经依法立案侦查**。这意味着系统启动时并不是从零开始，而是通常已经存在一批由侦查人员掌握、依法调取或人工整理出的基础实体和基础关系，例如：

- 已知案件
- 已知嫌疑人
- 已知密切关系人
- 已知账户
- 已知部分交易关系
- 已知部分通联关系

因此，领域本体生成不应被设计成“完全从零自由生成”，而应设计成：

**已有侦查事实作为先验输入 + LLM 在此基础上做补充、扩展和归纳。**

也就是说，本体层既要接住“已经知道的 entity 和 relation”，也要允许 LLM 基于材料继续发现：

- 原本未被显式标出的实体
- 原本未被串联出来的关系
- 原本未被归类的行为类型
- 分散在不同材料中的同一对象

在这里，LLM 的角色不是替代侦查人员定义对象，而是帮助我们在已有侦查框架上继续挖掘，得到可能原本未被发现的 entity 或 relation。

这里不建议完全自由生成，而建议使用：

**人工预设核心 schema + LLM 辅助扩展**

原因很简单：

- 比赛时间短
- 司法场景严谨
- 完全自由生成不稳定

所以最合适的做法是：

### 先人工确定核心实体类型

- 案件
- 犯罪嫌疑人
- 密切关系人
- 司法工作人员
- 单位机构
- 银行账户
- 资金交易
- 行为事件
- 电子文书
- 时间节点

### 再人工确定核心关系类型

- 任职于
- 参与案件
- 存在联系
- 存在资金往来
- 共同出现
- 使用同一账户
- 参与同一事件
- 与异常行为关联

### 最后让 LLM 做补充

LLM 负责补：

- 属性字段
- 细分关系
- 类型说明
- 抽取提示词

## 4.3 可以参考 MiroFish 的什么

`MiroFish` 的相关实现主要在：

- [ontology_generator.py](</c:/Users/adm14/Desktop/law_project/MiroFish/backend/app/services/ontology_generator.py>)

它做的事是：

- 把文档内容交给 LLM
- 让 LLM 输出 `entity_types` 和 `edge_types`
- 形成后续图谱构建可用的 schema

这套思路非常值得借，因为它把“先定对象，再做图谱”这个顺序做对了。

## 4.4 我们适合用什么技术

这里还要额外考虑两个现实条件：**大规模证据处理**和**涉密场景部署**。

第一，大规模证据意味着不能把所有材料一次性交给单个模型串行处理，否则很容易遇到：

- 上下文长度不够
- 处理速度过慢
- 成本过高
- 输出不稳定

所以更合适的做法是采用一种**工作流型 multi-agent / 多模块并行处理方式**。这里的 multi-agent，不是 `MiroFish` 那种成千上万个社会角色 agent，而是若干个职责明确的处理 agent，例如：

- 文本证据抽取 agent
- 表格证据解析 agent
- 实体归并 agent
- 关系补全 agent
- schema 校验 agent

这些 agent 可以并行处理不同证据块、不同数据类型，再在后端统一汇总结果。这样做的意义主要在于提升吞吐量、降低单点压力，并让大规模证据处理更具扩展性。

第二，这个场景天然可能涉及涉密或半涉密内容，因此方案表达上不应默认依赖公网模型服务，而应强调：

- 模型支持本地部署或私有化部署
- 后端系统支持内网环境运行
- 证据数据在本地闭环处理
- 上传、解析、抽取、查询和输出过程可做权限控制

也就是说，这一步最稳妥的技术口径应该是：

**采用本地化部署模型 + 多 agent 并行处理 + 后端结构化校验的方式完成领域本体生成与扩展。**

这一层最适合的技术其实很明确：

- 一个支持结构化输出的 LLM
- JSON schema 约束输出
- 一层人工预设的侦查场景 schema

技术组合上完全可以是：

- 本地部署或私有化部署的 `OpenAI-compatible` 模型服务
- 结构化 JSON 输出
- Python 后端做 schema 校验与结果汇总
- 多 agent / 多 worker 异步并行处理

必要时还可以加：

- Pydantic 做字段校验
- 人工审核开关
- 队列系统或异步任务系统

## 4.5 能不能做到

**能做到，但必须限制问题范围。**

如果我们的目标是：

- 自动生成完整法学本体
- 自动覆盖全部司法犯罪语义

那很难稳定。

但如果我们的目标是：

- 在固定的侦查场景里，补全“人、案、钱、行为、关系”这些核心对象模型

那是完全可做的，而且比赛阶段足够用了。

## 4.6 这一步的产出是什么

这一步做完后，应该产出：

- 实体类型定义
- 关系类型定义
- 每类实体的属性字段
- 每类关系的属性字段
- 后续抽取规则所依赖的 schema

一句话说，这一步产出的是：

**侦查场景的统一语义模型。**

## 5. 第三步：图谱构建

## 5.1 这一步要做什么

这一步解决的是“证据数据怎么变成人、案、钱、行为之间的结构化关系网络”的问题。

图谱构建不是简单画图，而是把前两步的结果真正组合起来：

- 证据数据提供内容
- 领域本体提供抽取目标
- 图谱构建把它们转成实体节点和关系边

## 5.2 我们的设计思路

这里需要补充一个重要判断：如果前面的证据解析和实体/关系抽取已经完成，那么这一层的重点确实会从“如何抽取”转向“如何落库、如何查询、如何可视化”。所以你的判断大方向是对的，但这一步并不完全是“有 node 和 edge 就自然完成”，中间还有几个很关键的工程问题：

- 同名实体如何归并
- 不同来源的关系如何去重并保留证据链
- 节点和边需要挂哪些属性，才能支持后续查询
- 图谱如何支撑后面的分析层和碰撞层，而不是只做展示

因此，图谱构建后半段真正要解决的是四件事：

- **存储**
- **查询**
- **可视化**
- **证据溯源**

关于 `Zep`，它是 `MiroFish` 当前使用的外部图谱/记忆相关服务，但不适合作为我们方案必须绑定的唯一技术。对比赛原型而言，更重要的是把“图谱思路”做出来，而不是依赖某一个特定平台本身。

所以这里更准确的表述应当是：

**前序模块完成实体与关系抽取后，图谱构建模块负责完成实体归并、关系落库、证据挂接、图谱查询和可视化输出，为后续分析层和碰撞层提供统一数据底座。**

这一步建议按三层做：

### 第一层：实体抽取

从文本和结构化数据里抽取：

- 人
- 案
- 单位
- 账户
- 交易
- 行为
- 时间点

### 第二层：关系抽取

根据本体定义抽取：

- 谁和谁有关系
- 谁和账户有关
- 谁参与了什么事件
- 哪笔资金流和哪类行为相关

### 第三层：实体归并与图谱落库

不同来源的数据里，同一个人、同一个账户、同一事件可能会重复出现。  
所以图谱构建不能只抽取，还必须做：

- 实体归并
- 去重
- 来源挂接
- 关系落库

在技术实现上，这一步完全可以不依赖 `Zep`。更可控、更适合比赛阶段的路线是：

- 后端把节点和边存进本地图数据库或关系型数据库
- 前端使用图可视化组件展示关系网络
- 查询层支持按人、按账户、按案件、按时间、按关系类型检索

因此，这一步真正难的不是“能不能画出来”，而是“图谱能不能被后续模块稳定使用”。这也是为什么图谱落库不是一个纯展示问题，而是一个存储、查询和证据组织问题。

## 5.3 可以参考 MiroFish 的什么

`MiroFish` 的相关实现主要在：

- [graph_builder.py](</c:/Users/adm14/Desktop/law_project/MiroFish/backend/app/services/graph_builder.py>)

它的基本工作流是：

1. 拿到已经定义好的 ontology
2. 对文本切块
3. 把文本块送入图谱系统
4. 让图谱系统基于 ontology 抽实体和关系
5. 返回图谱节点和边

也就是说，它的核心启发是：

**图谱构建不是手工写死规则，而是“本体约束下的自动抽取 + 图谱写入”。**

## 5.4 我们适合用什么技术

这一层大致有两种路线：

### 路线 A：参考 MiroFish，走图谱平台路线

- 使用类似 `Zep` 的图谱能力
- 由 LLM + 图谱平台完成抽取和写入

优点：

- 开发快
- 展示效果好
- 很适合比赛原型

缺点：

- 依赖外部平台
- 定制深度有限

### 路线 B：自己做简化版图谱构建

- LLM 做实体和关系抽取
- 后端自己存成图结构
- 前端自己做可视化

优点：

- 更可控
- 更适合定制碰撞逻辑

缺点：

- 工程量更大

如果按比赛节奏，我更建议先走：

**LLM 抽取 + 本地简化图谱存储**

因为这更容易和后面的分析层、碰撞层结合。

## 5.5 能不能做到

**能做到，但这里是处理层三步里技术难度最高的一步。**

难点主要有三个：

1. 实体抽取的稳定性
2. 关系抽取的准确性
3. 多源数据下的实体归并

不过如果我们控制范围，只围绕比赛题目最核心的几类对象做，是完全可以完成一个可展示、可答辩、可解释的原型的。

## 5.6 这一步的产出是什么

这一步做完后，应该形成：

- 实体节点
- 关系边
- 每个节点和边的来源证据
- 可查询的侦查图谱

一句话说，这一步产出的是：

**面向后续分析和碰撞的关系数据底座。**

## 6. 处理层最终结论

如果把整个处理层压缩成一句话，就是：

### 第一步：解析证据

把海量、多格式证据材料转成标准化中间数据。

### 第二步：生成领域本体

把侦查场景里“要抽什么、要连什么”定义清楚。

### 第三步：图谱构建

把证据数据和领域本体结合起来，形成可查询的侦查关系图谱。

## 7. 最后一句话

参考 `MiroFish`，我们在处理层最应该借的，不是它“有很多智能体”，而是它这条非常清楚的技术链：

**证据解析 -> 语义建模 -> 图谱构建**

这三步是能做、该做，而且非常适合比赛原型落地的。
