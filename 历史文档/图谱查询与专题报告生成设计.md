# 图谱查询与专题报告生成设计

## 1. 这份文档讨论什么

这份文档只先明确分析与碰撞层里的前两个功能：

1. **功能 1：图谱查询**
2. **功能 2：专题报告生成**

其中第二部分会重点说明：

- 报告如何生成
- 用什么技术生成
- 系统如何具体实现

## 2. 功能 1：图谱查询

## 2.1 为什么图谱查询必须有

图谱查询是分析与碰撞层的基础功能。  
如果没有查询能力，图谱只是一个静态存储结果，无法被侦查人员真正使用。

因此，图谱查询必须作为平台的基础能力先做出来。

## 2.2 图谱查询解决什么问题

图谱查询本质上解决的是：

- 如何快速找到某个对象相关的全部关系
- 如何沿着关系链找到间接关联对象
- 如何按案件、账户、时间、关系类型组织检索结果

这使得侦查人员可以从“看材料”切换到“查链条”。

## 2.3 图谱查询应该支持哪些能力

建议至少支持以下查询模式：

### 1. 人物关系查询

输入某个人物，输出：

- 直接关系人
- 间接关系人
- 所属案件
- 关联账户
- 关联行为事件

### 2. 账户关联查询

输入某个账户，输出：

- 账户归属对象
- 相关交易对象
- 交易时间分布
- 与案件和人物的关联链

### 3. 案件链路查询

输入某个案件，输出：

- 相关人员
- 相关账户
- 相关交易
- 相关行为节点
- 关键时间线

### 4. 时间线查询

输入某个时间段，输出：

- 该时间段内的人员行为
- 资金流动
- 通联或关系变化
- 与案件节点相关的事件

### 5. 关系类型查询

输入某一类关系，输出：

- 所有该类边
- 相关实体
- 证据来源
- 可能形成的链路

## 2.4 图谱查询适合用什么技术

这部分最适合的技术比较明确：

- 图结构存储或图查询接口
- 后端检索 API
- 前端图可视化组件

如果做比赛原型，不一定必须上专门图数据库。  
可以采用更稳妥的方案：

- 后端把节点和边存到本地数据库
- 后端提供人物、账户、案件、时间等查询接口
- 前端把结果渲染成关系图和列表

这就足够支撑比赛展示。

## 2.5 图谱查询的具体实现方式

建议这样实现：

### 第一步：定义查询入口

例如：

- `按人物查`
- `按账户查`
- `按案件查`
- `按时间查`

### 第二步：后端执行关系检索

后端从节点和边表中取出：

- 目标节点
- 相邻节点
- 相关边
- 边的证据来源

### 第三步：结果组织

后端把查询结果组织成两类输出：

- 图形化输出：节点 + 边
- 文本化输出：关键关系摘要 + 证据摘要

### 第四步：前端展示

前端用图谱视图展示关系网络，同时用表格或信息卡展示：

- 节点详情
- 关系详情
- 证据来源

## 2.6 图谱查询的最终作用

图谱查询是后续一切生成内容的基础。  
无论是资金报告、行为报告、关系报告还是综合报告，第一步都应来自图谱查询结果。

所以可以把它理解成：

**分析与碰撞层的基础功能 1。**

## 3. 功能 2：专题报告生成

## 3.1 为什么专题报告生成值得做

图谱查询解决的是“查出来”，但评委和用户真正更容易感受到价值的，是“生成一份看得懂的结果”。  
所以专题报告生成非常适合作为第二个核心功能。

它既响应题目里的：

- 参考信息
- 信息画像
- 参考建议

又能直接服务于 PPT 演示和答辩展示。

## 3.2 报告可以按哪些线路生成

建议做成“可选线路生成”的方式。

### 单线路报告

- 人物关系报告
- 资金流动报告
- 行为分析报告
- 时间线报告

### 多线路组合报告

- 资金 + 行为
- 资金 + 人物关系
- 人物关系 + 时间线
- 行为 + 时间线
- 资金 + 行为 + 人物关系

这种设计的好处是：

- 既能做专题分析
- 又能做综合分析
- 非常适合比赛演示时快速切换场景

## 3.3 报告生成到底怎么做

报告生成不能凭空让 LLM 写一篇文章，而应当采用下面这条链路：

**图谱查询 -> 结果组织 -> 模板化结构 -> LLM 归纳成文**

也就是说，LLM 负责“写出来”，但内容基础必须来自前面的图谱查询结果。

## 3.4 报告生成的具体实现方式

建议按四步做。

### 第一步：用户选择分析线路

例如用户选择：

- 资金流动报告
- 资金 + 行为联合报告
- 人物关系 + 时间线联合报告

这一步决定系统后面要查哪些数据。

### 第二步：后端按线路执行图谱查询

不同线路对应不同查询集合。

例如：

#### 资金线路

重点查询：

- 关联账户
- 交易链
- 交易时间分布
- 交易相关人物

#### 行为线路

重点查询：

- 行为事件
- 行为发生时段
- 与案件节点的关联
- 与人物关系的叠加

#### 人物关系线路

重点查询：

- 直接关系链
- 间接关系链
- 关键桥接节点
- 关系与资金或行为的重叠

#### 时间线线路

重点查询：

- 案件关键时间点
- 事件顺序
- 异常集中时段

### 第三步：后端把查询结果整理成报告上下文

这一步非常关键。  
后端不能直接把生 raw graph 全丢给 LLM，而要先整理成结构化上下文，例如：

- 关键对象清单
- 关键关系链
- 关键时间点
- 关键异常摘要
- 对应证据来源

也就是说，后端先做一次“结构化摘要”，再交给 LLM。

### 第四步：LLM 基于模板生成报告文本

此时 LLM 负责把结构化结果写成可阅读报告。

推荐使用固定模板，例如：

1. 报告概述
2. 关键发现
3. 重点关系/资金/行为/时间线
4. 异常线索摘要
5. 初步画像
6. 参考建议

这样做的好处是：

- 输出稳定
- 可控
- 容易答辩

## 3.5 报告生成适合用什么技术

这部分最适合的技术组合是：

- 图谱查询接口
- 后端结构化上下文拼装
- 模板化报告骨架
- LLM 负责文字生成

更具体一点：

- 后端：Python
- 数据来源：图谱节点与边 + 证据来源表
- 查询结果组织：JSON / Pydantic schema
- 文本生成：本地部署或私有化部署的 `OpenAI-compatible` LLM

如果追求更稳，可以把 LLM 输出限制成：

- 固定章节
- 固定字段
- 限制语言风格

## 3.6 为什么这套方案可做

因为这不是让模型“凭空思考”，而是一个比较稳的工程链路：

1. 查询是确定性的
2. 结构化整理是确定性的
3. 模板是确定性的
4. LLM 只负责把已有信息写成自然语言

所以它的风险远小于完全开放式生成。

## 3.7 报告最终可以输出什么内容

报告输出建议分成四类：

### 1. 参考信息

- 关键关系链
- 可疑资金流向
- 重点行为节点
- 异常时间段

### 2. 信息画像

- 犯罪嫌疑人画像
- 密切关系人画像
- 账户画像
- 行为画像

### 3. 联合分析结论

例如：

- 资金与行为在关键时间段发生重叠
- 人物关系链与资金链存在交叉
- 行为事件与案件节点同步出现

### 4. 参考建议

- 建议重点核查对象
- 建议重点关注时间窗口
- 建议优先复核的关系链或交易链

## 3.8 我们如何强调“支持只选某几个维度生成”

这一点可以明确写成系统特色：

本系统支持按专题线路和按组合线路生成报告，既可单独生成人物关系报告、资金流动报告、行为分析报告、时间线报告，也可根据侦查需求对多个维度进行联合分析并输出综合报告。

这是一个很好的展示点，因为它说明平台不是死板的固定报告器，而是可配置的分析输出系统。

## 4. 这两个功能之间的关系

可以把它们理解成：

- **功能 1 图谱查询**：负责“查”
- **功能 2 专题报告生成**：负责“写”

进一步说：

- 图谱查询是基础能力
- 专题报告生成是高价值输出能力

所以比较稳的技术链是：

**图谱查询 -> 结构化整理 -> 模板化组织 -> LLM 生成报告**

## 5. 一句话结论

如果把前两个功能压缩成一句话，就是：

**先通过图谱查询完成对人物、账户、案件、时间线等对象的关系检索，再基于查询结果按专题线路或组合线路生成结构化分析报告，输出参考信息、信息画像和参考建议。**
